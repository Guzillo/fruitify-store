# Fruitify Store — backend

REST API for an online fruit store. The project covers user registration and sign-in (JWT),
a product and category catalog, a shopping cart, order placement, admin order management and
Stripe Checkout payments.

The API documentation is generated by **springdoc-openapi** and available in Swagger UI.

## Tech stack

| Area | Technology |
|---|---|
| Language / runtime | Java 25 |
| Framework | Spring Boot 4.1.1 (Spring Web MVC) |
| Security | Spring Security, OAuth2 Resource Server, JWT (RSA), `USER` / `ADMIN` roles |
| Persistence | Spring Data JPA, Hibernate |
| Database | PostgreSQL 18 |
| Migrations | Flyway (`src/main/resources/db/migration`) |
| Payments | Stripe Java SDK |
| API documentation | springdoc-openapi 3.1.1 + Swagger UI |
| Testing | JUnit 5, Mockito, AssertJ, Testcontainers 2.0.5 |
| Build | Maven |

## Running the application

Requirements: JDK 25, Docker (for the database) and `openssl`.

```bash
# 1. Database
docker compose up -d db

# 2. RSA keys used to sign JWTs (the certs directory is gitignored)
mkdir -p src/main/resources/certs
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 \
  -out src/main/resources/certs/private.pem
openssl rsa -pubout -in src/main/resources/certs/private.pem \
  -out src/main/resources/certs/public.pem

# 3. Environment variables
export STRIPE_SECRET_KEY=sk_test_...
export STRIPE_WEBHOOK_SECRET=whsec_...

# 4. Start the application (the dev profile adds demo data)
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

- Application: `http://localhost:8080`
- Swagger UI: `http://localhost:8080/swagger-ui.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`
- OpenAPI YAML: `http://localhost:8080/v3/api-docs.yaml`

The `dev` profile provides demo accounts: `user@email.com` / `pass1` and
`admin@email.com` / `pass2` (along with a few sample products).

### Configuration

| Property | Meaning |
|---|---|
| `spring.datasource.url/username/password` | PostgreSQL connection |
| `spring.jpa.hibernate.ddl-auto=validate` | the schema is validated rather than created by Hibernate |
| `rsa.private-key`, `rsa.public-key` | PEM keys used to sign and verify JWTs |
| `stripe.secret-key` | Stripe API key |
| `stripe.webhook-secret` | secret used to verify the `Stripe-Signature` header |
| `stripe.domain` | frontend base URL used in the Stripe return URL |

## Authentication

1. `POST /api/auth/signup` — registration (assigns the `USER` role).
2. `POST /api/auth/signin` — sign-in with **HTTP Basic** (`email:password`). Returns `accessToken`
   and `refreshToken`.
3. Send `Authorization: Bearer <accessToken>` to all other endpoints.
4. `POST /api/auth/refresh` — issue a new access token from a refresh token.
5. `POST /api/auth/logout` — revoke a refresh token.

In Swagger UI click **Authorize**: use `bearerAuth` for JWTs and `basicAuth` only to test
`/api/auth/signin`. The `ADMIN` role inherits `USER` permissions.

## Endpoints

### Authentication

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/api/auth/signup` | public | Register a user |
| POST | `/api/auth/signin` | Basic | Sign in; returns an access and a refresh token |
| POST | `/api/auth/refresh` | public | Issue a new access token |
| POST | `/api/auth/logout` | public | Revoke a refresh token |

### Users

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/api/users/me` | Bearer | Profile of the signed-in user |
| PUT | `/api/users/me` | Bearer | Update the profile |
| PUT | `/api/users/me/password` | Bearer | Change the password |

### Products and categories

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/api/products` | public | Product list (paginated) |
| GET | `/api/products/{productId}` | public | Product details |
| POST | `/api/products` | ADMIN | Create a product |
| PUT | `/api/products/{productId}` | ADMIN | Update a product |
| DELETE | `/api/products/{productId}` | ADMIN | Delete a product |
| GET | `/api/categories` | public | Category list |
| POST | `/api/categories` | ADMIN | Create a category |
| DELETE | `/api/categories/{categoryId}` | ADMIN | Delete a category |

Inactive products are visible only to users with the `ADMIN` role.

### Cart

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/api/cart` | Bearer | Cart contents |
| POST | `/api/cart/items` | Bearer | Add a product to the cart |
| PUT | `/api/cart/items/{itemId}` | Bearer | Change an item's quantity |
| DELETE | `/api/cart/items/{itemId}` | Bearer | Remove an item |
| DELETE | `/api/cart` | Bearer | Clear the cart |

### Orders

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/api/orders` | Bearer | Orders of the signed-in user (paginated) |
| POST | `/api/orders` | Bearer | Create an order from the cart |
| GET | `/api/orders/{orderId}` | Bearer | Details of the user's own order |
| GET | `/api/admin/orders` | ADMIN | All orders (paginated) |
| PATCH | `/api/admin/orders/{orderId}/status` | ADMIN | Change an order's status |

Statuses: `PENDING` → `PAID` or `CANCELLED`, `PAID` → `CANCELLED`. Cancelling an order restores
product stock.

### Payments

|---|---|---|---|
| POST | `/api/payments/create-checkout-session` | Bearer | Create a Stripe Checkout session for an order |
| POST | `/api/payments/webhook` | public | Stripe webhook, verified with the `Stripe-Signature` header |

## Pagination and sorting

List endpoints accept `page`, `size` and `sort` parameters (for example
`?page=0&size=20&sort=name,asc`). The default `size` is `20`, the maximum is `100`.

- products: `id`, `name`, `price`, `stockQuantity`
- user orders: `createdAt`, `totalAmount`
- admin orders: `createdAt`, `totalAmount`, `status`

An unsupported sort property returns `400 Bad Request`.

## Example purchase flow

1. Sign up and sign in to obtain an access token.
2. Add products with `POST /api/cart/items`.
3. Create an order: `POST /api/orders` (status `PENDING`, product stock is decreased).
4. Create a payment session: `POST /api/payments/create-checkout-session` with the order
   identifier (the `orderNumber` field).
5. After payment, Stripe sends the `checkout.session.completed` webhook and the order status
   changes to `PAID`.

## Errors

The application returns an appropriate HTTP status and a readable error message. Request
validation errors use Spring's standard format, while business errors (such as insufficient
stock) are described in the response body. The most common codes are: `400` (validation / invalid
sorting), `401` (missing or invalid token), `403` (missing role), `404` (resource not found),
`409` (business conflict, e.g. insufficient stock) and `503` (Stripe unavailable).

## Database and migrations

The schema is managed exclusively by Flyway. Migrations live in
`src/main/resources/db/migration` and follow the `V<n>__DESCRIPTION.sql` naming convention.
Do not edit migrations that have already been applied — add new ones instead. Hibernate runs
with `ddl-auto=validate`, so any mismatch between entities and the schema prevents the
application from starting.

## Tests

```bash
./mvnw test
```

The tests require neither a local database nor a running `docker compose` — Testcontainers
starts a `postgres:18` container and runs the Flyway migrations against it. The container is
shared across the entire test run. A working Docker installation and the RSA keys generated in
[Running the application](#running-the-application) are required.

For faster local runs you can reuse the container between test runs:

```bash
TESTCONTAINERS_REUSE_ENABLE=true ./mvnw test
```

or add `testcontainers.reuse.enable=true` to `~/.testcontainers.properties`.

Test structure:

- `@WebMvcTest` — controller layer and security, without a database,
- `@SpringBootTest` + Testcontainers — repositories and service integration against a real
  PostgreSQL instance,
- unit tests — service logic with Mockito (no Spring context).

In a production environment, consider disabling public access to the documentation by setting
`springdoc.swagger-ui.enabled=false` and `springdoc.api-docs.enabled=false` (or protecting those
paths in `SecurityConfig`).
